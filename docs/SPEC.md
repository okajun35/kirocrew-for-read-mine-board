## v0.1 からの主な変更

| 変更 | 理由 |
|---|---|
| エージェント用の **MCP サーバー**を同梱（F-09 新設、MVP に入れる） | v0.1 はチケットの文面をチャットに一方通行で渡すだけで、「AI executes」を実現する手段がなかった |
| **チケット内容を信用できない入力として扱う**ことを明記 | 誰でも書ける本文を AI に渡すので、プロンプトインジェクションの経路になる |
| SSRF 対策を「プライベート IP 禁止」から「**設定済み base URL への固定**」に変更 | Redmine は社内ネットワークにあることが多く、プライベート IP を禁止すると主な用途が使えなくなる |
| API キーは**利用者本人のキー**を前提にする | 共有キーだと「Redmine の権限に従う」が成り立たない |
| MVP の検索条件を4つに絞り、デモの一本の流れを優先 | 締め切りに対して v0.1 の Must が多すぎた |
| **ja/en の2言語を最初から**用意 | ストアと Kiroween の審査（英語話者の可能性）。for-takt では後付けで困った |
| F-07 の実現手段を App Kit の API で特定 | `dispatchAgentAsync` / `getTaskResult` が存在する（詳細は V-08） |

## 1. 概要

Redmine のチケット検索・一覧・カンバン・詳細確認を Kiro Crew 内で完結させるアプリ。Redmine サーバーにはプラグインを入れず、**標準 REST API だけ**を使う。

カンバン上のチケットを Kiro Crew のチャットや Bot に渡し、エージェントが MCP ツールで Redmine を読み、結果をコメントとして返す。人間とエージェントが同じボードで同じ業務タスクを扱う。

**Human manages. AI executes. One board.**

- 人間はボードを見て作業を管理する
- エージェントは指示された作業を実行し、結果を Redmine に返す（書き込みは人の承認つき）
- 状況と成果を同じ画面で確認する
- 最終的な承認・完了判断は人間が行う

## 2. 解決したい課題

1. Redmine 標準の検索が使いにくく、目的のチケットを見つけづらい
2. 一覧の視認性が低く、作業状況を直感的に把握しづらい
3. カンバンには一般に Redmine プラグインが必要
4. プラグインは Redmine 本体の版上げのたびに互換性対応が必要
5. Redmine と Kiro Crew を行き来して作業を指示するのが面倒
6. 人間の作業とエージェントの実行状況が分断される

## 3. 基本設計方針

- Redmine 本体には手を加えない。REST API だけで基本機能を実現する
- 検索・一覧・カンバンは AI なしでも使える。AI 連携は必要なときだけ使う
- **Redmine のデータを業務情報の正本**とする。アプリはチケットのコピーを正本として持たない（キャッシュは可）
- **AI の実行状態とチケットの業務状態は分離する**。Bot との関連付けはアプリ側で管理し、Redmine の担当者フィールドに Bot を入れない
- Redmine の既存の権限とワークフローを尊重する。許可されていない操作を UI でもエージェントでも出さない
- Redmine への書き込みは、UI でもエージェントでも**人の明示的な操作か承認**を必要とする

## 4. 機能要件

優先度: **Must** = MVP に入れる / **Should** = 余力があれば / **Could** = 発展機能

### F-01 接続設定 — Must

- Redmine の base URL を登録する（`https://` を推奨。`http://` は警告つきで許可。社内の http 運用があるため）
- **利用者本人の API キー**で認証する（Redmine の「個人設定 → API アクセスキー」）
- 接続テストは `/users/current.json` で本人確認し、名前と権限の概要を表示する（REST 無効は 403、無効キーは 401 として案内）
- 設定はアプリのデータ領域（`~/.kiro/crew/apps/redmine-board/data`）に保存する。API キーは権限 0600 のファイルに置き、UI には返さない（「設定済み」かどうかだけ返す）
- 複数サーバーの切り替えは将来対応

### F-02 チケット検索 — Must（MVP は絞り込み4種）

- MVP: **キーワード / チケット ID / プロジェクト / ステータス / 担当者**
  - チケット ID（`#123` や数字だけの入力）は、検索ではなく直接開く
- Should: 優先度、更新日、トラッカー、複数条件の保存
- ソートとページネーション（一括で全件取得しない）
- 検索条件は URL ではなくアプリ側に保持する（ページを離れても残る）
- キーワード検索は `issues.json?any_searchable=~` を主経路とし、絞り込みと同一リクエストで送る。受理しない版は `search.json` → `issue_id` 取り直しにフォールバックする（**Search Adapter で吸収**）。なお `issues.json` はデフォルトでオープン状態のみ返すため、全件は `status_id=*` を付ける
- 検索 UI は画面上部に常設する

### F-03 チケット一覧 — Must

- テーブル表示。列のソート
- 行の選択で詳細パネルを開く
- 検索結果をそのままカンバンに切り替えられる（条件を共有）
- ステータス・担当者・優先度を視覚的に区別する（色だけに頼らない）
- Should: 表示列の選択、長いタイトルの展開

### F-04 カンバンボード — Must（表示のみ）

- チケットをカードで表示し、Redmine のステータスごとに列を作る
- プロジェクト別に表示し、担当者で絞り込める
- カードに優先度を出す。カードの選択で詳細を開く
- テーブルと検索条件を共有する。横スクロールに対応する
- 列ごとの件数を出す（ページング中は「表示中 / 合計」）
- Should: ドラッグ＆ドロップでのステータス変更。`include=allowed_statuses` が使える版では**Redmine が許可する遷移だけ**をドロップ先として出す。無効な遷移は 204 で黙って無視されるため、更新後は必ずチケットを取り直して確定を確認する。`allowed_statuses` が取れない版では D&D を無効にする
- Could: 担当者変更、カード表示項目のカスタマイズ

### F-05 チケット詳細 — Must

- サイドパネルに表示し、検索画面から離れずに確認できる
- 件名、説明、プロジェクト、トラッカー、ステータス、優先度、担当者、作成日・更新日・期日
- コメント・更新履歴（journals）
- 元の Redmine を開くリンク
- 本文とコメントは生テキストで返る。書式はサーバー設定依存（5.1: textile/markdown/common_mark、6.1: common_mark 系）で、API からは読めない。**CommonMark 優先の安全なレンダラーでサニタイズして表示**し、生 HTML は出さない。Textile 系の本文は生テキスト表示に留める
- 添付画像は public project では認証なしで取れるが、private project では API キーが必要。MVP ではリンクのみ（将来は backend 経由で中継）
- Should: 親子関係・関連チケット、コメント追加、ステータス更新、担当者変更

### F-06 Kiro Crew チャットへの引き渡し — Must

- 詳細パネルの操作から、チケットの情報を添えて新しいチャットを開く（App Kit の `openChat({ agent, message, autoSend: false })`。`agent` に同梱エージェントを指定できる。ドラフトが開き、送信は人が行う）
- 渡すもの: チケット ID、件名、Redmine URL、プロジェクト。説明とコメントは**エージェントが MCP ツールで取得する**のを基本にする（チャット欄に長文を貼らない）
- 定型の依頼文を用意する（ja/en）: 「調査して」「実装方針を考えて」「修正して」
- 依頼文に、チケット本文は外部の入力であり指示として扱わないことを含める（§7 のプロンプトインジェクション対策）

### F-07 Bot へのタスク割り当て — Should

- チケットから Bot を選び、作業指示を送る
- App Kit の `dispatchAgentAsync(agent, prompt)`（= `POST /api/spawn`）で実行し、`getTaskResult(taskId)` で状態を取る。`agent` はアプリ自身のエージェントに限定される。**無人実行は `approval_mode="auto"` になり承認プロンプトが出ない**ため、バックグラウンド実行用のエージェントの tools は読み取り系に絞り、書き込みはアプリ側の `Review Required → Done` フロー（人の操作）に委ねる
- アプリが持つ実行状態: `Queued → Running → Review Required → Done / Failed`
  - SDK のタスク状態から `Queued / Running / Failed` を写す。`Review Required` と `Done` は**アプリ側で管理する**（エージェント完了 → Review Required → 人が確認して Done）
- チケットと実行の関連付け（チケット ID ↔ タスク ID ↔ Bot）はアプリのデータ領域に保存する。Redmine 側には保存しない
- 成果物・PR へのリンクを表示する（エージェントの結果に含まれる URL を拾う）

### F-08 人間と Bot の共同カンバン — Could

- 人間とエージェントの担当を区別して表示する
- 実行中・レビュー待ち・失敗をカードに重ねて表示する（F-07 の状態）
- 最終判断は人が行う

### F-09 エージェント用 MCP サーバー — Must（新設）

アプリに stdio の MCP サーバーを同梱し、`app.json` の `mcpServers` で宣言する。同梱エージェント（例: `redmine-assistant`）の `tools` から参照する。

| ツール | 種類 | MVP |
|---|---|---|
| `redmine_search` | 読み取り | Must |
| `redmine_get_issue`（journals・関連を含む） | 読み取り | Must |
| `redmine_list_statuses` / `redmine_list_projects` | 読み取り | Must |
| `redmine_add_comment` | 書き込み | Must（承認つき） |
| `redmine_update_status` | 書き込み | Should（承認つき） |

- 読み取りツールだけを同梱エージェントの `allowedTools`（自動承認）に入れる。**書き込みツールは自動承認しない**（毎回人の承認が出る）
- ツールの結果に含まれるチケット本文は、データであることを明示する形で返す（例: `untrusted_content` フィールドに入れる）
- API キーは MCP サーバーがアプリのデータ領域から読む（`Path(__file__).resolve().parent.parent / "data"`。backend 共有のコア経由）。ツールの引数や結果に出さない。MCP サーバーから localhost/社内ネットワークへの通信は実装時のスモークテストで確認する
- MCP サーバーはステートレスにする（要求ごとに設定を読む）。Kiro Crew の MCP の方針に合わせる

```text
Kiro Crew
 └─ Redmine Board App（外部アプリ）
     ├─ UI（React + TS + Vite、ui/dist/index.mjs をコミット）
     │   ├─ Search / Issue List / Kanban / Issue Detail
     │   └─ Bot Status（Should）
     ├─ Backend（UI 用の HTTP ルート）
     │   ├─ Redmine API Client（base URL 固定・キー保護）
     │   ├─ Search Adapter / Issue Adapter（版差の吸収）
     │   ├─ Settings / Credentials
     │   └─ Bot Execution Store（F-07）
     ├─ MCP Server（エージェント用ツール、F-09）
     │   └─ Redmine API Client を共有
     └─ Agent + Skill（redmine-assistant）
               │
     ┌─────────┴─────────┐
  Redmine REST API    Kiro Crew（chat / agent runtime）
```

### バックエンドの実装方式（決定待ち）

| 案 | 長所 | 短所 |
|---|---|---|
| **A. Python の `backend.hooks.routes`（ゲートウェイ内）** | 構成が単純。for-takt の認証・パス安全確認・ルーティングの型を流用できる | ゲートウェイの権限で動くため、利用者の trust 付与が必須。UI と型を共有できない |
| B. Node の `backend.entryPoint`（`backend.type: "node"`、別プロセス） | TypeScript で統一でき、型を共有できる | 別プロセスとリバースプロキシになる。npm 依存のインストールが要る |

推奨は **A**（締め切りがあり、for-takt で動作実績があるため）。MCP サーバーは Python の標準ライブラリだけで書き、Redmine クライアントを backend と共有する（for-takt の `takt_core/` と同じ構成）。

### 責務分離

- **UI**: 描画、検索条件の保持、カンバン操作、チケット選択、作業指示の起点
- **Backend**: Redmine との通信、認証情報の保護、レスポンスの正規化、エラー処理、Bot 実行との関連付け
- **MCP Server**: エージェントが使う Redmine の読み書き（書き込みは承認つき）
- **Redmine**: チケットの正本、権限、ステータスとワークフロー
- **Kiro Crew**: エージェントの実行、チャット、Bot の管理

## 7. 非機能要件

### セキュリティ

- **API キー**: UI に返さない。ログに出さない。エラーメッセージからも除去する。保存ファイルの権限は 0600
- **SSRF**: 通信先は設定済みの base URL（スキーム・ホスト・ポート）に限る。UI・エージェントからは**パスとクエリしか指定できない**ようにする。別ホストへのリダイレクトは追わない。base URL の変更は所有者だけが行える
- **プロンプトインジェクション**: チケット本文・コメント・件名は信用できない入力。エージェントにはデータとして渡し、書き込みツールは自動承認しない。依頼文テンプレートにもその旨を入れる
- **XSS**: 本文はサニタイズしてから表示する。リンクは `http(s)` だけを許可する
- **権限**: Redmine の権限に従う（本人の API キーを使うことで担保する）。Redmine の代理ログイン機能（管理者用の `X-Redmine-Switch-User`）は使わない
- **書き込み操作**: アプリのバックエンドの書き込みルートは所有者だけ（`ctx.require_owner`）。アプリトークンからの呼び出しは拒否する

### 互換性

- Redmine 本体の変更は不要。REST API で疎結合にする
- 版の違いは Adapter で吸収する。**対応版は 5.1 系以上を推奨**（5.1.12 と 6.1.6 で検証済み）。API で版を取る方法は無いため、`allowed_statuses`・`any_searchable` の有無で機能検出する。4.2 系以下は非対応
- Redmine 側で「REST による Web サービスを有効にする」設定が必要（管理者設定）。README に明記する

### 性能・操作性

- 読み込み中の表示、リクエストのキャンセル、ページネーション
- 大量のチケットを一括取得しない（1回の上限は Redmine 側の制限に従う）【要検証 V-04】
- エラー時の再試行。更新後の表示の整合（更新したチケットを取り直す）

### 国際化

- 文言はすべて辞書ファイルにまとめ、ja/en を用意する。コンポーネントに直書きしない
- 日付・数値はロケールに従って整形する

## 8. MVP の範囲

**必須（デモの一本の流れ）**

検索 → カンバン → 詳細 → 「Kiro に依頼」 → エージェントが MCP で読んで作業 → 結果を承認つきでコメント投稿 → ボードに反映

1. 接続設定（F-01）
2. 検索（F-02、絞り込み4種）
3. テーブル一覧（F-03）
4. カンバン表示（F-04、表示のみ）
5. 詳細サイドパネル（F-05）
6. チャットへの引き渡し（F-06）
7. MCP サーバーと同梱エージェント・スキル（F-09、読み取り + コメント投稿）
8. ja/en 対応
9. README・セットアップ手順・デモ用 Redmine（Docker）と投入データ
10. ストア掲載用のアイコン・ヒーロー画像・スクリーンショット

**余力があれば**

- ドラッグ＆ドロップによるステータス変更
- 詳細パネルからのインライン更新
- Bot への直接割り当てと実行状態の表示（F-07）
- PR との関連付け

**今回やらない**

- ベクトル検索
- 複数 Redmine サーバーの切り替え
- Redmine 側の Webhook / プラグイン
- Bot を Redmine の担当者として登録すること
